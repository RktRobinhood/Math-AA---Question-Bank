# Candidate families for Question Studio #46

The current bank has 1,466 unique canonically tagged archived question records across the four courses. Of these, 1,304 have at least two tagged parts. Counting only each part’s first syllabus topic, 387 change primary topic from one part to another, 134 place Functions before Calculus, and 38 include a Functions → Calculus → Functions progression. These are inventory filters, not proof of mathematical dependency or counts of publishable templates. Shared SL/HL appearances are not counted twice; the course counts therefore refer to record origin, not all appearances. No question prompt, question image, or solution was used in the analysis.

Use the counts to find high-yield candidate structures, then inspect an authorized source privately and abstract its **shape**, without copying the math story, numbers, wording or graphics:
1. Identify visible production by a student, stable given data and invisible compiler intermediates separately.
2. Mark each edge as reading the stated given, reading a visible earlier result, or internal computation only. A “hence” reference is not interchangeable with a model input.
3. Define of each exposed output the type (numeric, function, point, interval, conclusion), units, domain and assumptions. Distinguish symbolic exact values and numeric approximations.
4. Match the shape to existing node family or propose a new shape when key prerequisites differ. Verify separately for course and assessment profile, using the actual syllabus, calculator expectations, command language and demand.
5. Ship only original authored cases with checked constraints, counterexamples and valid seeds. Being able to build many questions does not establish infinite or uniformly good variants.

Start with **model → differentiate → choose and interpret an optimum**; contrast with **graph → identify intersection → interpret** and **sequence → cumulative value → first crossing**. These are genuinely different decision shapes. Build three to five families and check the printed paper and key before considering any wide conversion. Existing archive crops remain read-only. On the current site the paper basket already stores selections locally; evaluate a typed custom entry with immutable snapshot alongside its existing archive-ID entry type, not a replacement of archive items.
